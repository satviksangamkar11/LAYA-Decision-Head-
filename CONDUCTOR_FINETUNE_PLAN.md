## 1. What the model answers
One yes/no question per step: **"Did the agent stop in the middle of the task with work clearly left undone?"** (`should_continue`).
Used as the Laya-coder sidecar arm of the agent test (PLAN.md 13.5): when the agent proposes to finish, a high P(TRUE) means "do not accept the finish, keep going".

## 2. The model (frozen facts, `models/laya-conductor/rl_agent_config.json`)

|---|---|
| Base | `mvilacad/laya-conductor`, revision `04116e6808345ee4aa9477afa5e405cd48ab8421`, Apache-2.0 |
| Weights check | `model.safetensors` sha256 `3c8bed1ad91e90151b38fefb3a5625e02307ce491f1eb11659bcdde05e4f1d7e`, asserted in the notebook |
| Encoder | `answerdotai/ModernBERT-large`, 421M params, plus a 2-layer typed head (`head_layers` 2) |
| Limits | `max_len` 1024 tokens total, `head_max_len` 256 tokens for the question and options |
| Library | `laya==0.3.22` |
| Shipped temperatures | `[1.3608, 1.2, 1.4666]` for (choice, score, noul); index 2 is the one used here |

### Input to the model
`[CLS] noul question: <instruction> [SEP] [MASK] false: no, the statement does not hold [MASK] true: yes, the statement holds [SEP] <state> [SEP]`
- The instruction is the conductor's own question, copied exactly (`teachers/laya_teachers.py` `CONTINUE_Q`): "Did the assistant stop in the middle of the task with work clearly left undone? TRUE only if the response says it will do more next, lists remaining steps it has not done, or ends mid-implementation. FALSE if it reports the task as finished, asks a question, or reaches a natural stopping point."
- `<state>` is the state dict serialised by `json.dumps`, and `build_sequence` keeps the HEAD of it (`truncate_left` False), so anything past the budget is cut from the END of the JSON. Field order therefore matters: `last_response`, `last_observation`, `task`. The task field is the one expected to be cut.

### Output of the model
- Two logits, one at each [MASK] marker: (false, true). Probability = softmax(logits / temperature[2]).
- `laya.Agent.predict(state, questions)["answers"]["should_continue"]["noul"]` = **P(TRUE) = P(should continue)**, a float in [0, 1]. Option order is always [false, true].
- A second output, `act_head`, exists but is dead on this repo's data (`act_probability` always 1.0). It is not used.
- On a T4 (compute capability below 8) the library autocasts fp16 whatever `amp_dtype` says (checked in `laya/agent.py`), so the shipped `bf16` setting does not matter there.

## 3. Data
Source: `nebius/SWE-rebench-openhands-trajectories`, file `trajectories.parquet`, 2.08 GB, CC-BY-4.0, 67,074 trajectories, generated by Qwen3-Coder-480B (not by our backbone). Downloaded inside Kaggle by the CPU notebook. A local copy is in `data/nebius_swe_rebench/` (user yes, 2026-10-03).
Columns used: `trajectory_id`, `repo`, `resolved`, `exit_status`, `trajectory` (OpenAI-style message list).

### Selection (CPU notebook, BUILT, NOT RUN)
| Parameter | Value |
|---|---|
| Eligible trajectories | `exit_status == "submit"` only |
| `TARGET_TRAJ` | 4000, half resolved (2000) and half unresolved (2000); the official recipe used 4,105 items |
| `PER_REPO_CAP` | 12 trajectories per repo |
| Shuffle seed for picking | `random.Random(1)` |
| Test split | repo-disjoint: `sha256(repo) % 100 < 20`, so about 20% of repos; asserted `repo_overlap == 0` |
| Min length | a trajectory needs at least 3 assistant steps, else skipped |

### Rows per trajectory
4 rows: the last assistant step, the one before it, and `K_MID = 2` random earlier steps (`random.Random(2)`). So 4,000 trajectories give about 16,000 rows before skips (UNMEASURED until the CPU notebook runs).

### Fields in each row's state
| Field | Content | Cut |
|---|---|---|
| `last_response` | the assistant message at step `t`: its text plus every tool call as `[tool NAME] ARGS` | last 1000 chars (`RESP_CHARS`) |
| `last_observation` | the most recent tool result BEFORE step `t` (test output, command output) | last 900 chars (`OBS_CHARS`) |
| `task` | the first user message (the issue) | first 600 chars (`TASK_CHARS`) |

Local check on the 300-row sample (1,200 rows): 1.0% of states cut by the 1,024-token window, response tail lost 0.0%, observation tail lost 0.0%, longest sequence 1024.
Leak rule (A4 v1.1): the state may hold the message at `t` (that is what the question judges) and earlier tool results; never later events. `resolved`, `model_patch`, `exit_status` are never in the state.

### Label
`should_continue` TRUE (probability 1.0) at every sampled step, except FALSE (probability 0.0) only at the **final step of a resolved trajectory**. An unresolved trajectory's final "finish" is TRUE (premature or wrong stop).
- By construction one row in four of a resolved trajectory is FALSE, so FALSE is about 12.5% of rows with the balanced selection. Measured on the 300-row sample: 11.7%.
- **Consequence:** accuracy on all rows is meaningless (always answering TRUE gets about 87.5%). Report AUROC, ECE, and the final-steps-only subset, which is 50/50 by construction.
- **Known tension (OPEN, accepted):** the question text says FALSE if the response "reports the task as finished", but an unresolved finish is labelled TRUE. The model has to learn "claims finished but the evidence says otherwise", which is why `last_observation` was added. If the final-steps result is no better than the state-blind control, this label design has failed and we stop.
- Rows carry `trajectory_id`, `repo`, `split`, `step`, `n_steps`, `is_last`, `resolved` as metadata only (never model input).

### Training items and calibration cut (GPU notebook, BUILT)
- Train rows are tokenised with `build_sequence(tok, state, question, 1024, 256)` into items `{ids, markers, qtype (noul = 2), target [p_false, p_true], label, repo}`. Items whose marker count is not 2 are skipped and counted.
- Calibration cut: train repos with `sha256("cal:"+repo) % 10 == 0` (about 10%), repo-disjoint from the training items (asserted). Replaces the official script's random cut of 400 training rows.
- `SMOKE = True` keeps 600 train items and 100 calibration items and runs 1 epoch (timing run only).

## 4. Training (official script `train_ddp.py`, patched only for the calibration file)
| Parameter | Value |
|---|---|
| Hardware | Kaggle GPU T4 x2, `torchrun --standalone --nproc_per_node=2`, DDP (NCCL), `find_unused_parameters=True` |
| Epochs | 4 (`EPOCHS`); 1 in SMOKE |
| Batch | micro-batch 8, accumulation 4, so 32 per GPU per update and 64 per update across 2 GPUs |
| Optimizer | AdamW, encoder lr 2.5e-5, head lr 1e-4, weight decay 0.01 |
| Schedule | cosine to 1e-6 over `(items per GPU // 32) * epochs` steps; no warmup |
| Precision | fp16 autocast, `GradScaler`, grad clip 1.0 |
| Memory | gradient checkpointing on (encoder and head); `max_len` 1024, `head_max_len` 256; `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` |
| Loss | `loss_rl + 1.0 * loss_ce`, divided by the accumulation count |
| RL part | 4 noise samples per item, noise sigma falls linearly 0.4 to 0.1 over the epochs; reward = `proper_reward` (log score + 0.75 x spherical score; RPS weight 1.0 applies to score-type questions only, so unused here); advantage = (reward minus mean over samples) / std |
| CE part | cross-entropy against the soft target |
| Data order | rows split across ranks by `train_items[rank::world]`; `random.seed(42 + epoch + rank)` per epoch |
| Seeds | no global torch seed is set, so DDP runs are not bit-reproducible; record this |
| Checkpoints | after each epoch to `laya_conductor_ft/checkpoint_latest` (fp16); final to `laya_conductor_ft` |
| Temperature refit | after training, LBFGS on the calibration cut (lr 0.1, 100 iterations), clamped to [0.1, 10], written into `rl_agent_config.json` as `temperature` for (choice, score, noul); only index 2 is fitted |
| Run time | UNMEASURED. The shipped config says 1.96 h for 7,313 updates; its card says about 30 min for 4,105 turns. Use SMOKE to measure seconds per step first |

## 5. Evaluation (GPU notebook, BUILT, NOT RUN)
Test rows: all final-step test rows plus up to 1,500 other test rows (shuffle seed 3), from the repo-disjoint test split. Counts print at run time.
Each model is scored on (a) all used rows and (b) **final steps only** (resolved finish versus unresolved finish). (b) is the number that matters.

| Row | Meaning |
|---|---|
| Fine-tuned conductor | the result |
| Original conductor (zero-shot) | same weights, no training; shows what fine-tuning added |
| State-blind control | TF-IDF + logistic regression on the `task` text only; the head must beat it |
| Shuffled-state control | the fine-tuned model with `last_response` and `last_observation` shuffled across rows (pairs kept together), labels kept; must fall toward chance |

Metrics printed per row: accuracy, AUROC (`roc_auc_score`), ECE (10 bins), n. The repo-disjoint split is the third shortcut check (asserted in both notebooks).
- **OPEN (needs your number before the first run, CLAUDE.md: thresholds committed before any comparison):** the margin the fine-tuned final-steps AUROC must beat the state-blind control, the shuffled control and the zero-shot conductor by; and the ECE ceiling. I have not invented one.
- NOT BUILT yet: a repo-clustered bootstrap interval on the final-steps AUROC difference (needed because rows from one trajectory are not independent).

## 7. Run order and stop rules
1. CPU notebook (Accelerator None, Internet ON). Check `conductor_rows_summary.json`: repo_overlap 0, FALSE share near 12.5%, final-step test row count, test repo count. Stop if any is off.
2. GPU notebook with `SMOKE = True`. Read seconds per step, GPU memory, any skipped items. Then set `EPOCHS` and `TARGET_TRAJ` from the measurement.
3. GPU notebook full run. Download outputs.
4. Compare the table. **Stop rule:** final-steps AUROC not above the state-blind control, or the shuffled control not near chance, means the conductor has not learned from the state; do not ship it into the agent test, inspect labels and evidence first.
5. Only a conductor that passes goes into the sidecar arm of the agent test.

## 11. Research for the best stop/decision sidecar (2026-10-04; abstracts and model cards only, full papers NOT read; numbers are [A])
- `Fail-Fast, Restart-Smart` (arXiv 2608.03222): a 0.6B monitor reads OBSERVABLE PREFIX TEXT (no policy logits, no hidden states), trained with terminal AND dense fail-to-pass supervision on Qwen3.6-27B trajectories; saves 14.6-20.4% of execution tokens at 5% false positives; transfers to three other policies including a closed API one; restart lifts resolution 66.6% -> 71.8% (cold restart 66.8%). Supports a text-only sidecar and a model in the 0.4-0.6B class.
- `Steer, Don't Solve` (arXiv 2606.21811): fine-tuned 4B and 8B critics (SFT + DPO) give high-level guidance every k steps; +5.6% to +16.0% resolved rate across six agents (e.g. +16.0% GLM-4.7-Flash, +14.4% GPT-OSS-120B) on SWE-bench Verified. A generative critic, not a classifier.
- `OpenHands/openhands-critic-32b-exp-20250417`: Qwen2.5-Coder-32B + regression head, labels from unit tests, TD objective (gamma 0.99) pushing the final outcome back through the trajectory; 60.6% single run, 66.4% picking among 5. Too large for us. `agentica-org/DeepSWE-Verifier`: Qwen3-14B, patch ranking.
- `Before the Rollout Ends` (arXiv 2609.31995): rubric-based early reward from the prefix; no model size in the abstract.
What this changes: (1) our `value` label (final outcome copied to every step) is the weakest supervision in this literature; dense step signals (tests flipping fail->pass, visible in `last_observation`) and TD-style targets are what the strong monitors use. Laya already ships `td_lambda_targets` (laya/common.py) for multi-turn trajectories. (2) a Qwen3-0.6B-class monitor reading a LONGER prefix than ModernBERT's 1,024 tokens is a credible challenger; not on disk (Qwen3-0.6B is about 1.2 GB bf16 [estimate], needs your yes). (3) judge by early-stop token savings at a fixed false-positive rate and by resolved rate, not accuracy.
